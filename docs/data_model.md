# Data model

```
bronze   raw files, never changed          data/bronze/{source}/dt={date}/{hash}.html|json + .meta.json
silver   cleaned tables, one row per thing DuckDB: silver_*  (written by Python, contracts/silver.yml)
gold     marts for readers                 DuckDB: fct_*, dim_*  (built by dbt, exported as parquet)
ops      what happened and how long        DuckDB: ops_*
```

The lineage between the dbt models is in [lineage.md](lineage.md) (generated from the dbt project).

## Bronze

The path is a function of (source, run date, URL), so a second write of the same page replaces the
same file. The `.meta.json` next to a file (status, content hash, fetch time) is written last and is
the commit marker: a data file without it is an incomplete write and counts as missing.

## Silver (Python, `contracts/silver.yml`)

| Table | One row per | Key |
|---|---|---|
| `silver_vacancies` | vacancy on a site (DOU or Djinni), latest version | `id` (`dou:123`, `djinni:456`) |
| `silver_vacancy_sightings` | vacancy and day it was on a listing page | `vacancy_id, seen_date` |
| `silver_vacancy_groups` | real vacancy: a group of the same posting on the two sites (size, which member gives the text and which the salary) | `dedup_group_id` |
| `silver_skills` | skill of the taxonomy (with its parent) | `skill_id` |
| `silver_vacancy_skills` | vacancy, skill and method (`dictionary` or `llm`) | `vacancy_id, skill_id, method` |
| `silver_nbu_rates` | currency and date | `rate_date, currency` |
| `silver_dou_salaries` | survey answer with a salary | `_source_file, row_no` |
| `llm_cache`, `silver_llm_terms`, `silver_unknown_skills` | LLM answer by cache key; the skill words the model used; skill words the taxonomy lacks | see the contract |

`silver_vacancies` keeps the parser's fields (title, company, category, locations, declared salary,
description) next to what later steps derive from them: `salary_min/max/currency` and `salary_usd_*`,
`seniority` (from the title), `experience_years_text` and `english_level` (from the description) and
`dedup_group_id`. A vacancy fetched later replaces an earlier version; a backfill of an older day never
overwrites a newer one.

## Gold (dbt, `warehouse/`)

| Model | One row per | Notes |
|---|---|---|
| `stg_*` | | thin views over silver |
| `int_vacancies_deduped` | real vacancy | text from DOU, salary from Djinni, earliest listing date |
| `int_skill_ancestors`, `int_group_skills`, `int_group_skills_rolled_up` | | a skill counts for its parents (Next.js also counts for React) |
| `fct_vacancy_daily` | vacancy and day while it is open | `new`, `active`, `closed` (two days off the listing); the first day of data is flagged `left_censored` |
| `silver_vacancies_history` (snapshot) | version of a vacancy | SCD2: a row is added when the title, salary or description changes |
| `fct_market_daily` | date, source, category, level | open, new and closed vacancies |
| `dim_skill` | skill | |
| `fct_skill_demand_monthly` | month and skill | share of that month's real vacancies |
| `fct_skill_pairs` | pair of skills | count, lift, PMI, NPMI (pairs with enough support only) |
| `fct_salary_by_skill` | skill | p25/p50/p75 of declared salaries (only with enough vacancies) |
| `fct_salary_survey` | year, role, level | weighted survey percentiles (only with enough respondents) |
| `fct_vacancy_lifetime` | level | how long closed vacancies stayed open |
| `ml_features_salary` | survey answer | the features of the salary model |

Every mart has an enforced column contract and tests (`unique`, `not_null`, `relationships`,
`accepted_values` and two custom ones). Marts do not publish samples that are too small; the minimum
sizes are variables in `warehouse/dbt_project.yml`. The seeds `position_map` and `city_map` turn the
free-text survey positions and cities into a small vocabulary. They are generated by
`jobmarket make-seeds` and can be corrected by editing the CSV.

`export` writes the marts to `data/export/*.parquet` and adds `skill_clusters.parquet` (Louvain
communities of the pair graph) and `last_update.json`.

## Ops tables

`ops_pipeline_runs` (a flow run), `ops_task_runs` (a step or task attempt), `ops_scrape_runs`,
`ops_dq_results` and `ops_llm_usage`. See [observability.md](observability.md).
